- **The cyber verification worklist is packaged into 4 paste-ready bundles, and its header was lying about its own state** (`scripts/build-cyber-bundles.mjs`, `docs/claims-to-verify-cyber/bundles/`, D-052). The 369 outstanding cyber claims already had nine per-class packs; what they did not have was a delivery shape that survives contact with a chat window.
  - **One paste is the wrong unit, and the reason is output rather than input.** 369 rows fit in ~30k tokens going in, but every `OK` must return a verdict **plus a URL plus a quote that settles the row** — so the reply is roughly **2.5×** the prompt, and a single paste asks for ~75k tokens back. **This is not hypothetical: D-038 records the IT pass's 160-row table coming back verified through row 152 and stopping.** Nine separate pastes fix the truncation and reintroduce D-038's *other* failure — a folder where nothing says which packs are done. Four numbered bundles are the shape that avoids both.
  - **`build-cyber-bundles.mjs` generates them and asserts its own invariants.** Rows in must equal rows out (**369 = 369**, checked), each bundle must carry the full rules block (a bundle whose rules silently differed from its neighbour's would be a handover defect, so the script **refuses to merge and throws**), and output is clean LF/UTF-8 with no BOM. Re-running regenerates from the packs, so the bundles cannot drift from their source.
  - **Send order is by expected yield, not by pack number.** Standards/frameworks leads because it is both the largest class (**98 rows**) and the most rot-prone — D-038 calls a versioned standard summarised in a beginner curriculum *"a time bomb with a long fuse"*, and the **OWASP A09 defect** already found in this repository was exactly that class. Command and cmdlet usage is deliberately split out alone (**bundle 03, 48 rows**) because **that is the class that produced 3 of the 3 real defects on the IT pass**, all sharing one shape: right name, broken invocation.
  - **The document's header contradicted its own body, in the direction that matters for a worklist.** `CYBER-CLAIM-VERIFICATION.md` was titled **"IT track — technical claim verification"** and stated **"verification NOT yet performed"** — both stale, because the file was copied from the IT one and generalised. The status was false toward *understating* the work: the docbody records 43 verified rows and a result table. **A worklist whose header disagrees with its own body is precisely the handover defect D-038 exists to prevent**, so it now states 43 of 373 done, 369 outstanding, and the stale *"216 claims need a source"* figure was corrected to **373** (the nine `needs checking` rows sum to 373; the packs carry 369 rows because the 43 already-verified ones overlap).
  - **The 43 already-verified rows are left in the bundles deliberately.** Marking them done would mean hand-maintaining `doneThrough` for three classes whose verdicts currently live in a conversation rather than in the repository, and **D-038 records that the done-state is hand-maintained on purpose because a script that guessed would fail in the worst direction: silently skipping unverified rows.** Re-verifying 43 known-clean rows out of 369 costs little; skipping an unknown number of unverified ones is how a claim class goes unchecked while appearing closed.
