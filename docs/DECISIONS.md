# Decisions

A lightweight decision log (ADR-style). Newest first.

## D-021 — Tasks carry a duration band, and the dashboard asks how long you have

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** The dashboard has always answered "What should I do today?" with the next unfinished checklist item that fits the reader's energy level. It could not answer a question a real beginner asks every day: *I have forty minutes. Is this a forty-minute task?* The curriculum's practice tasks ranged from "plug in a USB stick and watch Device Manager" to "install VirtualBox and build an Ubuntu VM" to "practise 20 technical interview questions across 8 topics", and nothing in the data distinguished them. A reader with half an hour was handed the VM. The obvious fix — a per-task minute count — was rejected only after research, not by assumption.
- **Decision:** Every practice task carries an authored duration **band**, not a number, in its metadata comment: `<!-- id: <PHASEID>-t<NN> band: <BAND> energy: <ENERGY> -->`. Four bands: `quick` (under 30 min), `focused` (30–90 min), `deep` (over 90 min), and `ongoing` (**not a single sitting** — recurring, week-gated, multi-session, or hardware-gated work). The dashboard asks how long the reader has, persists the answer as a preference, and offers a task whose band fits.
- **Consequences:**
  - **Bands, not minutes, because the underlying data is coarse and pretending otherwise would be a lie in the opposite direction.** 82% of the 183 practice tasks sit between 20 and 90 minutes, so any cut inside that range would be an arbitrary line drawn through a continuum — a 45-minute task would be "wrong" against a 44-minute estimate and no reader could tell. Only two honest edges exist: **under ~20 minutes** is essentially empty (4 tasks, 4%), and **over ~90 minutes** is *structurally* different rather than merely longer — multi-session projects, tool-curriculum cliffs, and writing volumes that cannot be finished in one sitting whatever the reader's pace. Phase-level durations (weeks, or "60–80 hours") were rejected as two to three orders of magnitude too coarse to schedule a Tuesday afternoon. Word count and verb choice were measured and carry almost no signal: two tasks both 27 words long differ sixfold in real time, and "Install VirtualBox" (90 min) sits in the same phrasing family as "Install CrystalDiskInfo" (20 min).
  - **Every band is an authored estimate, and the UI says so on the page.** Nobody has timed these tasks. Presenting a guess with the visual confidence of a measurement is the failure this label exists to prevent — a reader given a "45 minute" task that is really a three-hour install concludes the curriculum is unrealistic, not that the number was invented. The time control carries a visible note to that effect, and the smoke test asserts the word *estimate* survives on the rendered page.
  - **`ongoing` is an exclusion path, not a long duration.** More time does not turn a weekly retake into a sitting, and offering one as "today's task" would set the reader up to fail at it. `fitsBand` therefore fails closed on `ongoing` in both directions — it is never offered, and it is never treated as fitting.
  - **A real defect, caught by the new test rather than by a reader.** The first `pickToday` collapsed three different reasons into one "does not fit": a task needing longer, an `ongoing` commitment, and a task with no band at all. An unaddressed `ongoing` task left `smallestBlocking` null and fell through to `all-addressed`, so the dashboard would have told a reader **"nothing left" while they still had work** — just not work that fits in one sitting. That is the one sentence this page must never get wrong. The taxonomy was split instead of the test being relaxed: `only-ongoing` and `unjudged` now exist as distinct reasons with their own honest messages, and `test-today.mjs` asserts that leftover `ongoing` work never renders as everything being done.
  - **The picker walks curriculum order and never reorders.** It does not prefer larger tasks, smaller tasks, or the reader's favourites, and it does not shuffle. The suggestion is the first unaddressed task whose band fits, which keeps "what should I do today" answerable and stable across reloads.
  - **"Addressed" reuses what already exists and introduces no second progress system.** A task counts as addressed under exactly two rules: it has a non-blank answer in the notes store (D-019), or it belongs to a phase whose checklist is fully ticked. A phase with an *empty* checklist is guarded against — it must not read as complete, or a malformed phase would silently swallow its whole task list.
  - **The suggestion is drawn from practice tasks, and progress is still counted from the checklist.** The two lists are different on purpose: a checklist item is a claim about oneself ("I can use 20 basic Linux commands") and a practice task is an instruction ("Run `ss -tulpn` and identify listening services"). Only the second has a duration. The dashboard is the one place they meet, and the progress ring it shows is unchanged.
  - **`allPracticeTasks(track)` in [`data/roadmaps.js`](../learning-site/src/data/roadmaps.js)** is the read side, and [`lib/today.js`](../learning-site/src/lib/today.js) is pure — no React, no DOM — so the whole picker is exercised under plain Node in [`scripts/test-today.mjs`](../learning-site/scripts/test-today.mjs), 77 checks across fitting in both directions, the addressed rules, ordering, and every reason.
  - **The time budget is a tenth `localStorage` key** (`cs-roadmap:time-budget:v1`), registered in `transfer.js` → `KEYS` so a backup carries it, and owned by [`hooks/useTimeBudget.js`](../learning-site/src/hooks/useTimeBudget.js). It is a *preference*, like energy mode, so a merge keeps this machine's value rather than the incoming one. Its default is `focused`, because that is where 82% of the tasks actually sit and so is the least wrong guess for a reader who has never touched the control.
  - **`ongoing` is not offered as a time budget.** It is a property a task can have, not an amount of time a person can have, and offering it would let a reader select a budget the picker fails closed on — a control that appears to do nothing.

## D-020 — The shared documents are reachable, and the reader's writing is readable back

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** Two halves of the same problem. (1) `career-roadmaps/shared/` — the anti-burnout rules, the 42-resource list, and the weekly tracker template — has always been part of the curriculum and had **no path to it from the site**, because `build-content.mjs` walks for `*-phase-*.md` and these are not phase files. The reader those documents were written for, someone on a 34–112 week plan at risk of burning out, was the one least likely to ever see them. (2) D-019 shipped the writing side and deliberately no reading side: a note was reachable only by navigating to the phase that owned it. Writing that can only be found by remembering where you put it is a silo, not a workspace.
- **Decision:** Two views. **Shared** renders the three shared documents from a new build artifact, `shared.json`. **Your work** gathers every phase note and every per-task answer from all 23 phases into one page, with a link back to the phase that owns each one. Neither view counts what it shows.
- **Consequences:**
  - **One parser, two corpora, via a `headingBase` parameter.** Lessons are authored inside a `## Lesson:` wrapper, so their headings start at level 3; a standalone shared document is authored `# Title` / `## Section`, so it starts at level 1. Rather than fork the parser, [`scripts/lesson-ast.mjs`](../scripts/lesson-ast.mjs) takes `headingBase` and [`scripts/shared-content.mjs`](../scripts/shared-content.mjs) passes 1. The build **fails** on an unparsed block in a shared document, so a document that drifts out of the expected shape stops the build rather than shipping half-rendered.
  - **The Shared view deliberately does not reuse `<Lesson>`.** Lesson carries a table of contents with scroll-spy, per-section done controls, and a reading-position bar — all of it keyed by phase id and persisted through `useLessonProgress`. A shared document has no phase, no progress, and nothing to tick, so borrowing that machinery would mean inventing a fake phase id to hang state on. The blocks render directly, which is why there is a small local TOC rather than a reused one.
  - **The resource list renders as real anchors, from structured data.** `renderInline` deliberately does not autolink, so rendering the list as prose would produce 42 unclickable URLs — the document would look complete and be useless. `shared-content.mjs` parses `Name — https://url` lines and **fails the build** if the separator is wrong or a bullet appears before any category heading, because a silently mis-parsed catalogue is worse than a stopped build. The smoke test then asserts every single resource is an `href` and that no bare URL is left as text.
  - **Your work carries no denominator, and that is the point.** The summary says how many phases hold writing — a statement about *where things are*, with no "of 23", no percentage, no progress bar, and no ordering by volume. `summariseWork()` returns `{ phases, notes, answers, orphaned }` and deliberately has no `total`, `percent`, or `remaining` field, so the absence is structural rather than a rendering choice someone can undo by accident. A reader who wrote one line sees the same page a reader with 40 answers sees. This follows the same rule D-019 established for the writing side: a workspace that starts keeping score is a report card.
  - **Answers are matched by id and orphans are kept, not dropped.** An answer whose task no longer exists in the corpus is still the reader's writing; deleting it because the curriculum moved would be destroying the one thing on this site that cannot be regenerated. It is kept and flagged `orphaned: true`, and the page explains why it is there rather than presenting it as a normal answer.
  - **Your work reads via `readNotes()`, not `useNotes()`.** The hook owns the key and writes to it; a page that only displays is a second live copy of one `localStorage` key, and two live copies drift. This is the same discipline the dashboard rail follows with `readPortfolio()`.
  - **Both views are covered by the render smoke test, which found a real gap in the process.** A page whose entire content sits behind a click is invisible to server rendering — `Shared` holds the selected document in `useState`, so every render showed the first document and the resources list could not be covered at all. `Shared` gained an optional `initialId` prop, read only as the `useState` seed, so each document can be rendered directly. That is also the hook a future deep-link would need.
  - **Bundle cost: 20 KB for `shared.json`**, no new dependency. The two views are a page each plus one pure module.

## D-019 — The reader gets somewhere to write, and it is not scored

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** The curriculum constantly asks the reader to produce something. Nine phases were rewritten specifically so they end in an artefact the reader keeps — a baseline, a ticket log, an incident report, an interview story, a risk register. The site's entire support for that was **a checkbox**. A reader halfway through a 15,000-word lesson, looking at an exercise that says *write down what you noticed*, had nowhere in the site to write it: their notes lived in another app or nowhere, and the connection between the writing and the phase was lost. Worse, the tool that tracked their progress was the only thing that acknowledged the work, which taught the reader that the only work that counted was the work that could be ticked.
- **Decision:** A second local store — `cs-roadmap:notes:v1`, owned by [`hooks/useNotes.js`](../learning-site/src/hooks/useNotes.js) — holding one free-text note per phase and one answer per practice task. It is reached from the phase page: a **Your notes** panel, collapsed by default, and a **Write your answer** control on each practice task. Nothing in it is scored, counted, or reported anywhere else in the site.
- **Consequences:**
  - **It is a workspace, not a scoreboard, and that is enforced by a test.** There is no completion count, no "3 of 7 answered", no percentage, and nothing here feeds the dashboard. A reader who writes one line and one who writes nothing look identical to every other part of the site. `smoke-render.mjs` asserts that the rendered output of both new components contains no `N of M` or `N/M` pattern — a workspace that starts keeping score is the failure mode this decision exists to prevent, and it is the one an innocent later change is most likely to introduce.
  - **Practice tasks gained stable ids, which they never had.** They were emitted as plain numbered strings, so an answer keyed to a task had only its array position to go on — and inserting a task above it would silently move one reader's writing onto a different question. `scripts/build-content.mjs` now mints `<phase-id>-tNN` per task on the same principle the checklist already follows. **Honest limitation, recorded rather than hidden:** these ids come from position at build time, not from an authored `<!-- id: … -->` comment, so *appending* a task is safe and *reordering* one is not. The checklist solved this years ago by authoring ids in the Markdown; tasks have only ever been appended to, which is why it has not been needed yet. Migrating is a one-line change in that function when it is.
  - **The note and the answers merge differently, because they are different things.** A note is prose, and no machine can honestly choose between two paragraphs, so on import the existing note wins and an incoming draft is left alone. Answers are a map of id to text and union per task, existing winning on a collision. A phase that exists only in the incoming file is taken whole — that is the entire point of moving your work to a new laptop. All of this lives in `mergeValue` and is asserted in `scripts/test-notes.mjs`.
  - **An empty entry is pruned on write.** A phase the reader opened and typed nothing into does not appear in the store, and a note they cleared is removed rather than kept as an empty string. That keeps the backup file an honest description of what the reader has.
  - **It registered as the ninth key in `transfer.js` on the day it was written**, which is what that list was built for. Adding a key without registering it is exactly the silent omission `test-data.mjs`'s registry assertion exists to catch — and it did catch the follow-on: that suite hardcoded "eight keys" in five places and seeded only eight, so the ninth threw an unguarded `JSON.parse(undefined)` that took the whole file down with a stack trace naming neither the key nor the reason. The suite now reports a missing fixture value as a failed check instead of crashing, and the count assertions read nine.
  - **The panel and the answer boxes do not print.** D-017 exists so a phase can be taken to a train and annotated with a pen; a page already full of the reader's own earlier answers is a page with no room to write on. The tasks themselves still print, with blank space after each one.
  - **Bundle cost: 13 KB raw / 2.6 KB gzipped**, no new dependency. The store is a hook and two components; there is no library behind it.

## D-018 — In-lesson find is a second engine, not a second use of the first

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** Search (D-013) answers "where in the curriculum is this?" — a question asked *before* committing to a lesson. Once a reader is 15,000 words into one phase, the word they want is usually a few hundred words below them on the same page, and the corpus-wide box is a worse answer than scrolling: it switches views, and each result row loads its own lesson just to build a snippet. Browser find (Ctrl+F) is scoped correctly but cannot rank — it walks hits in document order, shows no context, and offers no jump-to-section.
- **Decision:** A second, smaller engine — [`lib/lessonSearch.js`](../learning-site/src/lib/lessonSearch.js) — that searches the block AST already in memory for the open lesson. It mirrors `useSearch.js`'s query semantics deliberately (same token regex, same trailing-punctuation strip, same exact-vs-loose tiers, same prefix and stem rules, same rarest-first intersection, same exact bonus) so the two boxes never disagree about what the reader typed. `components/LessonFinder.jsx` is the UI, collapsed by default behind a toolbar button because a reading page should not spend vertical space on a control used rarely.
- **Consequences:**
  - **Two deliberate divergences from the sibling engine, both because the corpus is one lesson instead of 23.** (1) `STOPWORDS` is a hard-coded grammatical list rather than a measured common set — a single lesson has no index to measure against. It deliberately does **not** include content words like `user` or `data`, which still discriminate inside one lesson; the corpus engine flags those, and copying that list here would widen a two-word query into a useless one. (2) An unresolvable term returns zero hits rather than tolerating it: across 23 lessons a missing term may be an indexing gap, but in one lesson it is simply absent, and the global box is the right tool.
  - **Section attribution is the nearest preceding h3/h4, and a heading owns itself.** A literal reading of "preceding" would attribute a hit inside `### Subnet masks` to the section above it, so a hit there would offer to jump to the wrong heading. h5 starts no section because `LessonBlock.jsx` renders it as a label with no TOC entry — attributing hits to a heading the reader cannot navigate to is worse than attributing them to the enclosing section. Blocks before the first heading get `sectionId: null` and are still indexed: the preamble is searchable prose, it just has no section to jump to.
  - **A snippet is three strings, not markup and not sentinels.** `{ before, match, after }` renders as three text nodes with the middle one emphasised, so the module never hands HTML to a caller that would have to trust it. Sentinel characters were rejected because a sentinel can legitimately occur in lesson text. `match` is the word as actually written, with sentence punctuation excluded.
  - **Every block type is indexed, including ones that do not exist yet.** Known types are handled explicitly; the `default` case walks any unrecognised block's string content with a depth cap, so a block that renders is searchable the day it appears. `buildEntries` emits exactly one entry per array position even for a malformed block, because skipping one would shift every later `blockIndex` and scroll the reader to the wrong place.
  - **`scripts/test-lesson-search.mjs` carries its own fixture** rather than reading `src/data/generated/lessons/`, which only exists after a build. It reproduces the shapes that have caused real bugs elsewhere — a sentence-final term carrying its punctuation, a nested bullet, an h5 that starts no section, a block before every heading — and asserts on section attribution, block-type reachability, ranking and snippet boundaries. The suite is in `npm test` as `test:lesson-search`.

## D-017 — A phase prints, because paper is the offline mode that already exists

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** The curriculum runs 34–112 weeks and the site is local-first by design (D-006), but "offline" had no answer for the case that matters most to a beginner: a train, a lab bench, a machine with no network, or simply a reader who wants to annotate a phase with a pen. None of that needs a service worker or a cache strategy, because the browser already has a mechanism for taking a page offline on paper, and the site had no `@media print` rules at all — a reader who hit Ctrl+P got the sidebar, the sticky toolbar, the reading bar and the dark theme.
- **Decision:** One `@media print` block at the end of [`styles/global.css`](../learning-site/src/styles/global.css), plus the finder styles above it. Everything that exists only to operate a browser is hidden — sidebar, off-canvas nav, topbar, reading bar, sticky lesson toolbar, in-lesson finder, per-section tick controls, code copy buttons, resume prompt, prev/next pager, and every modal or overlay. What prints is the lesson: prose, code, tables, the TOC, and the phase's structured sections.
- **Consequences:**
  - **The theme is repainted, not rewritten.** The site's own custom properties are overridden inside the print block (`--bg` to white, `--text` to black, and so on), so every component rule carries over instead of each one needing a print twin. The dark theme would empty a toner cartridge and is unreadable on a laser printout.
  - **Page-break rules are the substance of this decision, not the colour.** A code block split across a page boundary is unreadable and a table split mid-row is worse, so `break-inside: avoid` is applied to code, tables, blockquotes, list items and the table wrapper, and `break-after: avoid` keeps a heading with the text it introduces. A table that scrolls horizontally on screen has its wrapper set to `overflow: visible`, because a scrolled-away column on paper is simply lost.
  - **Link URLs are deliberately not expanded inline.** Appending the URL to every link would bury the prose in query strings; the curriculum's links are mostly documentation the reader looks up when back online.
  - **The reader's on-screen text size does not follow them onto paper.** The reading-size feature scales the lesson body through `--lesson-scale`, and a reader who set `A++` for a monitor would print a page with three paragraphs on it. Prose is pinned to 11pt and code and tables to 9pt.
  - **No dependency, no service worker, no cache.** The whole feature is CSS.

## D-016 — The reader's data is theirs to move, and an import is validated before it writes

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** Progress, portfolio, applications, schedule, reading position, section ticks and two preferences live in **eight** `localStorage` keys. The site is single-user and local-first by design (D-006), which is the right call — but it means a cleared browser profile, a new laptop, or a reinstall destroys months of work on a 34–112 week curriculum, and nothing in the UI said so. A reader could finish half a track and lose it to a routine "clear site data" without ever being warned.
- **Decision:** [`lib/transfer.js`](../learning-site/src/lib/transfer.js) exports all eight keys as one JSON document and reads that document back. `components/DataTransfer.jsx` is the panel, reached from the sidebar under **Data → Back up & restore**. Import is **validated before anything is written**, and a payload with one bad key is refused whole.
- **Consequences:**
  - **The module is pure, and that is what makes the rejection cases testable.** Storage is passed in as a two-method object rather than reached for as `window.localStorage`, so `scripts/test-data.mjs` exercises the entire round trip under plain Node — including the cases that matter, which are the failures. A backup format that silently accepts a malformed file and writes it over good data is worse than no backup at all.
  - **One bad key fails the whole import.** Half-restoring someone's progress and leaving the rest silently behind is the one outcome a backup must not have. Unknown keys are a different case and are *dropped and reported*, not refused: refusing the file over a key a newer version added would make forward compatibility impossible. A version mismatch is refused rather than half-read, for the same reason a failed validator is.
  - **Export omits rather than corrupts.** A key that is absent is not written at all; a key present but holding something this version cannot validate is omitted and listed in `skipped`, because exporting a corrupt value just moves the corruption to the file.
  - **Merge unions accomplishments and keeps this machine's position and preferences.** Progress, section ticks, portfolio and applications are things the reader made or finished, so losing one because another machine did not have it is exactly the failure this feature exists to prevent — they union. Reading position and the two preferences describe *this* device right now, and a merge that overwrote "where I am" with a stale value would yank the reader backwards on import. Existing wins on an id collision, so importing the same file twice is a no-op rather than a duplicate.
  - **Import is a modal, not a sidebar button next to "Reset progress".** It is the only action in the site that can overwrite the reader's work, and it does so across eight keys at once, so it shows the reader what the file contains key by key and applies nothing until they have seen that list. **Replace** exists for restoring onto a clean machine and is the second option, spelled out and confirmed.
  - **The page reloads after an import.** Every hook reads its key once at mount and then owns it in React state; an import writes `localStorage` underneath those live copies. Threading a refresh signal through eight hooks and getting it right in every one is more code and more ways to be partially correct than one reload after a settings errand.

## D-015 — The shell centres, and the dashboard gets a reference rail

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** With the reader affordances in place (D-014), the dashboard's remaining defect was visible before anything was read: on a 1,919px viewport it filled the left half and left the right half empty. Two causes, and they were separate.
  1. `.content` was capped at `--content-wide` (1,100px) and **left-aligned** against the sidebar. Even a page that wanted the width could not use it, and the dead band was a property of the shell, not of any page.
  2. The dashboard itself was a single column of cards. Nothing in it was wrong, but nothing in it was wide either — and the figures a reader actually checks (how far in, how long left, what is ready) were either absent or buried in prose.
  This matters more here than on a typical site because the curriculum is 34–112 weeks long. A reader returns for years; the page that answers "what should I do today" is the page they see most, and it was the least informative one.
- **Decision:** Two changes.
  1. **The shell centres and widens.** `--content-max` (1,400px) replaces `--content-wide` as the outer cap, applied with `margin-inline: auto`. `--content-wide` remains the cap for the one element allowed past the reading measure (tables). Centring is right here and left-alignment was not: every page is a column of cards, so the fix belongs to the shell.
  2. **The dashboard becomes two columns above 1,180px** — content plus a sticky **reference rail** carrying the progress ring, the plan's dates, three read-only readiness counts, and the next two phases. Phase cards also tile two-up once there is width for two honest cards.
- **Consequences:** The rail is the part that needs a boundary, and it has one. It is a reference column, not a second dashboard: no charts, no streaks, no leaderboards, per the anti-patterns in [`DESIGN-SYSTEM.md`](DESIGN-SYSTEM.md). Its only interactive elements are links to the page that owns each figure, and every count is phrased as "you have N" rather than "you are missing N".
  - **A rail that owns state would be a second source of truth.** The plan's dates come from `readStarts()`, the counts from `readPortfolio()` and `readApplications()` — plain reads, deliberately **not** the hooks. Two live copies of one `localStorage` key drift, and the stale one writing back would drop a record the reader just added on the page that owns it. The dashboard remounts on every view change, so a read at mount is correct; the hooks keep their subscribing behaviour for the pages that mutate.
  - **`fmtWeeks` and `fmtDate` moved into [`lib/pace.js`](../learning-site/src/lib/pace.js).** The rail and the Schedule page report the same numbers, and two copies of a formatter round them two different ways. `fmtDate` parses and formats as UTC, because formatting a UTC midnight in local time renders the previous day anywhere west of Greenwich — which turns a planned finish date into a wrong one.
  - **The ring is a chart, so it obeys the rule charts obey here.** The percentage and the raw count are rendered as text beside it; the `svg` carries a label rather than being silent; and it animates nothing. A non-numeric or out-of-range value clamps instead of reaching the dash arithmetic as `NaN`, which would render as no arc at all, silently — both cases are now asserted.
  - **Nothing is hidden at a narrow width.** Below the breakpoint the rail lays out as cards under the main column, in the same order. This is a reflow, not a truncation, and the 560px phone layout is unchanged apart from the phase grid dropping to one column.
  - **The main bundle grew by 4 KB raw / 0.7 KB gzipped** — 398 KB and 117.7 KB — because the ring and the rail add code and no dependencies. The search index is untouched.

## D-014 — Progress has two axes, and a phase remembers where you were

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** The site renders each lesson body in full (D-011) and ships it as its own file loaded on demand (D-012). Measurement afterwards exposed the shape of a problem that had been invisible while the lessons were only on GitHub: a lesson is **84–95% of its phase file**, IT Phase 1 alone has 66 `###`/`####` subheadings, and the longest runs ~15,500 words. Against that, the only completion signal in the application was the phase checklist — 7–19 items sitting **below** the lesson. A reader four hours into a lesson had no way to record that they had finished the section they were reading, no sense of how far in they were, and no way back to where they stopped. Meanwhile the phase page ended after its exit criteria with **nothing after it**: on a 9–14 phase track whose whole point is sequence, there was no "next" anywhere in the UI, and the only route to the following phase was to scroll to the top and aim at the sidebar.
- **Decision:** Three separate pieces of state, kept deliberately apart.
  1. **Lesson section state** ([`hooks/useLessonProgress.js`](../learning-site/src/hooks/useLessonProgress.js)), keyed by the heading id the lesson parser already emits and namespaced by phase id — `it-01#part-7`. Persisted under its own key, `cs-roadmap:lesson-sections:v1`.
  2. **Reading position** ([`hooks/useReadingState.js`](../learning-site/src/hooks/useReadingState.js)), recording the last phase opened and, per phase, the last heading on screen, under `cs-roadmap:reading:v1`.
  3. **Schedule start date** ([`hooks/useSchedule.js`](../learning-site/src/hooks/useSchedule.js)), one date per track, under `cs-roadmap:schedule:v1`.
  Navigation is derived, not stored: [`data/roadmaps.js`](../learning-site/src/data/roadmaps.js) gained `neighbours(track, phaseId)`, which reads the phase array's order rather than parsing titles.
- **Consequences:** The application gains a reason to distinguish *reading* from *completing*, and the distinction is enforced structurally rather than by convention — three storage keys, three labels, two counters on a phase page that never merge. This is the part worth recording, because the easy version of this feature is one progress bar, and one progress bar would make one of the two numbers lie: either section ticks would inflate the phase completion test the exit criteria depend on, or finishing a phase would silently discard the reader's place in a lesson.
  - **A heading id is the identity, and it derives from the heading text.** Rewording a heading retires its state rather than mis-attributing it — the same rule the checklist IDs follow ([`CONTENT-SCHEMA.md`](CONTENT-SCHEMA.md) → Checklist task IDs). A scroll offset was rejected for the same reason: an offset into content that can be regenerated is a number with no meaning after the next content edit.
  - **"Reset progress" does not clear reading state.** The button says "Reset all progress" and the reader means the checklist. Deleting their place in a lesson they were halfway through would be a surprise the label did not warn about.
  - **The resume prompt suggests and waits.** Nothing jumps on load. A reader who deliberately scrolled to the top has said something by doing so.
  - **The reading bar measures the lesson, not the page.** A document-scoped bar would count the checklist, tools, tasks, deliverable and exit criteria as reading, and would report a reader halfway through a lesson as a fraction of the whole page.
  - **A keyboard shortcut must not be able to change saved state.** Navigation, search and view switching are bound; checkbox toggling is not, and that omission is a decision rather than an oversight.
  - **`test-ui.mjs` was added because none of the existing guards could see any of this.** `smoke-render.mjs` runs no effects and no handlers, so it cannot observe a shortcut that never fires, a pace figure wrong by a week, or two phases colliding on a section key — and a collision would render a tick in one phase as a tick in another, which is invisible in every screenshot and every render assertion. The section-key namespacing has its own test for exactly that reason.

## D-013 — Search uses a build-time inverted index, not the lesson text

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** With 23 lessons rendering in the site, reaching a specific answer meant browsing — the sidebar gets you to a phase, not to the paragraph. Full-text search was the obvious next step, but the naive implementation is a trap here. The lesson JSON is 1.7 MB and is deliberately loaded one file at a time (D-012); an index that stored segment text was **measured** at 1,438 KB raw / **473 KB gzipped**, because it duplicated every lesson. An average lesson gzips to about 16 KB, so that index cost the reader roughly thirty lessons' worth of download for a feature used occasionally — the wrong trade for an audience on modest connections, which is exactly who this curriculum targets. A second attempt, windowing long segments with overlap to improve snippets, was also measured and made it **worse** (1,438 KB to 1,501 KB), because the overlap duplicated text.
- **Decision:** Emit an inverted index — term to segment id — and no prose. `scripts/search-index.mjs` builds it at build time into `generated/search.json`; `hooks/useSearch.js` fetches it once, lazily, on the reader's first search, and renders snippets from the lesson file the site already downloads when a phase is opened. Segments are cut at `###`/`####` headings, which lands a result on roughly a screenful and gives every hit a natural title. Postings are delta-encoded in base36 against document order. The index measures **471 KB raw / 180 KB as a delivered chunk**, and `index.html` does not reference it — the main bundle is unchanged at 105 KB gzipped, so a reader who never searches pays nothing.
- **Consequences:** The site gets search without undoing D-012. Three defects were found by testing the index against the query engine rather than by reading either one, and all three produced *silent* wrongness — a search box that returns nothing or the wrong thing without erroring:
  - **Pruned common terms.** Terms appearing in more than 20% of segments were originally *deleted* to save space. Since a query is an AND over its terms, one deleted term made the whole query return zero results: `"user account locked"` found nothing because `user` was gone. Common terms are now kept and flagged, so the engine matches them but does not let them narrow the result set, and the UI says which words it ignored.
  - **Punctuation glued into terms.** A sentence ending `"...was timestomped."` indexed the term with the period attached, so `timestomped.` and `timestomped` were different entries. Trailing separators are now stripped; interior punctuation is kept, because `get-adprincipalgroupmembership` and `page_fault_in_nonpaged_area` are exactly what a reader pastes in.
  - **Exact matches suppressed broader ones.** Searching `timestomping` matched only that exact term (modules 10 and 12) and never consulted the stem that would also have found module 11's `timestomped` — so typing *more precisely* returned *fewer* results. Exact and prefix matches are now collected separately and scored in tiers, with an exact-match bonus. Simply merging them was also wrong in the other direction: `STAR` exactly matches the interview method but also prefixes `start`, `startup` and `starved` (227 segments across all 23 lessons), and a merged set drowned the lesson that actually teaches STAR.
  - `learning-site/scripts/test-search.mjs` guards all three, plus ID range and ordering, empty and nonsense queries, and that every result points at a lesson file that exists. Like the lesson parser, a search bug does not crash the page — it just returns the wrong answer — so the guard has to assert on known-correct hits rather than on the absence of exceptions.

## D-012 — Lesson bodies are emitted per phase and loaded on demand

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** D-011 added the lesson body to the generated JSON. Measured afterwards, the lesson region is 84–95% of every phase file, and its JSON totals roughly 1.6 MB across both tracks. Because `src/data/roadmaps.js` imported the track files statically, Vite inlined all of it: the JS bundle went from 265 KB to 1.96 MB, so a reader who opened the dashboard downloaded the entire curriculum before seeing anything.
- **Decision:** Keep the track index files small (goal, skills, checklist, tools — about 200 KB total) and emit each lesson as its own file at `generated/lessons/<phase-id>.json`. The site loads one with a dynamic `import()` in `src/hooks/useLesson.js`, keyed by `phase.lessonPath` carried on the phase record, and caches per phase id in memory. The phase record also carries `lessonBlockCount` and `lessonHeadingCount` so the dashboard can describe a lesson without fetching it.
- **Consequences:** The initial bundle returns to ~340 KB and each lesson becomes a 30–170 KB chunk fetched when its phase is opened. This is the first split point in the app; a reader who never opens a phase never downloads a lesson. The cost is a loading state and an error state in `PhaseDetail`, and the requirement that `build-content.mjs` runs before the site is served — already true, since `dev` and `build` both call it. Vite needs a literal `import.meta.glob` pattern to discover the files, so the path is templated rather than computed.

## D-011 — The site renders the lesson body, not just the structured sections

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** `build-content.mjs` originally extracted goal, skills, topics, tools, tasks, checklist, and exit criteria — and dropped the `## Lesson:` region entirely. Measured per phase that region is 84–95% of the file, so the site was showing roughly a tenth of the curriculum: a checklist *about* a lesson rather than the lesson. The prose, the worked examples, and the tables were reachable only through a link to GitHub.
- **Decision:** Parse the lesson region into a block AST at build time with `scripts/lesson-ast.mjs`, and render it in the site with `components/Lesson.jsx` and `components/LessonBlock.jsx`, behind a table of contents built from the lesson's `###`/`####` headings. The Markdown stays the single source of truth; the AST is a build artifact like the rest of the JSON. No Markdown dependency is added — the parser supports the subset the curriculum actually uses, which was measured across all 18 phases before being written.
- **Consequences:** The site is now a reader for the curriculum rather than an index of it. Two guards protect the new path, because a parser bug does not crash anything — it just makes content vanish: `audit-lesson-ast.mjs` compares every lesson's AST against its source with markup stripped and fails on any loss or unrecognised construct, and `build-content.mjs` fails the build when the parser reports an unhandled construct. `smoke-render.mjs` renders the lesson for every phase and asserts that tables, code blocks, and headings all appear and that no literal `**` or backtick reaches rendered prose. Inline formatting needed one addition: the curriculum writes bold containing code (``**`/etc`**``), so `renderInline.jsx` now recurses into bold and italic runs instead of a single-pass alternation.

## D-010 — The sidebar is viewport-pinned, and becomes a drawer on small screens

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** `.app-shell` is a flex row and `.sidebar` had no height or position constraint, so the sidebar stretched to the full document height and scrolled away with the page. On a long phase the reader had to scroll back to the top to navigate. Below 720px the sidebar also stacked above the content, which pushed the page down and left the nav no closer.
- **Decision:** Give the sidebar `position: sticky; top: 0; height: 100vh; overflow-y: auto` so it stays pinned and scrolls independently. Below 860px, replace the stacked layout with an off-canvas drawer: fixed, translated off-screen, opened by a hamburger button in a sticky topbar, and closed by the backdrop, the close button, or Escape. Background scroll locks while it is open and the open phase is scrolled into view in the list.
- **Consequences:** The nav is reachable from any scroll position. The drawer adds one piece of state to `App.jsx` and needs Escape handling and scroll locking to avoid trapping the page behind an overlay — both are in place. View changes now reset scroll to the top, which also fixes opening a phase at the previous page's scroll offset.

## D-009 — Publishing the site to GitHub Pages, and the base path that makes it work

- **Date:** 2026-09-15
- **Status:** Accepted
- **Context:** D-008 permitted CI but ruled deployment out of scope and noted that "publishing the site would need a decision of its own." This is that decision. The site is a static Vite build, so it can be hosted anywhere; the constraint that shapes the rest is that GitHub Pages serves a *project* site from a subdirectory of a shared domain — `https://markkramm.github.io/cs-roadmap/` — rather than from a domain root.
- **Decision:** Publish the site to GitHub Pages from a dedicated `.github/workflows/deploy-pages.yml` workflow. Because the site is served from a subdirectory, `learning-site/vite.config.js` reads `process.env.VITE_BASE` and falls back to `/`, and the Pages build sets `VITE_BASE=/cs-roadmap/`.
- **Consequences:** Rule 3 in `AGENTS.md` gains a third bounded carve-out: `.github/workflows/` may now contain a deploy step, but only to GitHub Pages, and only for the built site. The content stays dependency-free — the deploy publishes generated output and adds nothing that reading `career-roadmaps/` depends on. Vite emits absolute asset URLs, so without the prefix the published page loads blank and every `/assets/...` request 404s; the workflow therefore *verifies* the emitted HTML and fails the build if the prefix is missing, rather than trusting the environment variable. Hard-coding the prefix was rejected because it would break `npm run dev`, `vite preview`, and the Netlify build, all of which serve from a root. Netlify is left working and unchanged as a fallback host.

## D-008 — CI is permitted, deploy is not

- **Date:** 2026-09-11
- **Status:** **Superseded by D-009** for the deploy question only; the CI carve-out still stands as written.

## D-007 — View navigation is local state, not a router

- **Date:** 2026-09-11
- **Status:** Accepted
- **Context:** M2 adds three destinations (tools library, portfolio tracker, application tracker) alongside the dashboard and the per-phase detail view. D-006 left routing open. The site is a single-user local tool: no server, no shareable URLs, no deep links, no analytics. A router would add a dependency and a URL surface to solve problems this tool does not have.
- **Decision:** Keep navigation in `App.jsx` as a single `view` string — `dashboard` | `phase` | `tools` | `portfolio` | `applications` — alongside the existing `trackId` and `openPhaseId`. No router dependency.

The browser's back and forward buttons do not move between views; the sidebar and the in-page Back button are the only navigation, which is why both stay visible on every view. If deep links are ever wanted, the switch in `App.jsx` is the single seam to replace — no component below it needs to change.
- **Amended by D-014:** the view list gained `schedule`, and keyboard shortcuts now reach every view — but navigation is still local state, and the browser's back button still does not move between views. D-014 added a second, complementary route through the content (`j`/`k` between phases, `g d` and `g s` between views) rather than a URL surface.

## D-001 — Normalize all text files to LF

- **Date:** 2026-09-11
- **Status:** Accepted
- **Context:** Mixed CRLF/LF caused whole-file diffs and obscured real changes.
