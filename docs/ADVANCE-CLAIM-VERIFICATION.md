# Advanced track — technical claim verification

**Status: VERIFIED — 508 rows, 444 `OK`, 17 `WRONG`, 47 `UNVERIFIABLE`, none outstanding.**

This is the third track verified, and the first whose verdicts are **reproducible from disk**.
`scripts/record-advance-verdicts.mjs` reads them back out of the worklist packs rather than
carrying a hardcoded copy, so the rows below are not a transcript of a conversation — they are
re-derivable. That is the difference from the IT track, whose verdicts were never written into
its document and whose header read "verified" over 225 empty verdict columns for sixteen days.

**Seventeen claims were wrong.** Every one is fixed in the corpus, and every `WRONG` verdict was
re-checked against the primary source before any content changed — D-038: *a model's answer
remains not a source*. **Four of the seventeen are one defect repeated**, and they are the most
valuable thing this pass found, because three of them were invisible in a different track's
already-completed verification. See "What the pass found" below.

Nothing in this repository has ever tested whether its content is technically *true*. Every
guard tests internal consistency — does the parser lose content, do cross-references resolve,
does a table sum to the number the prose claims. The comprehension passes test whether a
beginner can *follow* the text. Both are blind to a sentence that is perfectly consistent,
perfectly clear, and factually wrong.

The one error of that class found so far (`modbus.func_code >= 15`, which also matches function
code 43 and every exception response) was caught by a reader who happened to know Modbus. That
is not a method. This file is the method: every checkable claim, in one place, with its
location, so the checking is finite work instead of a re-read of 160,000 words.

## How to verify

For each claim below, fetch the source named for its class and compare. Then fill in the
verdict line. Three outcomes, and the third is the important one:

| Verdict | Meaning |
|---|---|
| `OK` | The claim matches the source. Quote the source line that settles it. |
| `WRONG` | The claim contradicts the source. Give the correct value **and** the source. |
| `UNVERIFIABLE` | The claim is a judgement, an analogy, or a simplification rather than a fact. |

**`UNVERIFIABLE` is a real result, not a failure to try.** A phase may say a `/26` is "the point
where most beginners close the tab" — that is pedagogy, not a fact, and marking it OK would be
laundering an opinion into a verified column. Sorting those out honestly is what makes the
`OK` column mean anything.

## What the pass found

**Seventeen wrong claims, in seven classes, and the most instructive one is a defect four
identical copies of.** `date: 2026/03/14` and `modified: 2026/03/14` appeared in **six** places
across three phases, because the specification mandates ISO 8601 with dashes and the normative
JSON schema constrains the value with a regex slashes cannot match. **Phase 07 was already
conformant** — the corpus contradicted itself, and no guard could see it, because each guard
checks the text against itself.

Seven phases of verification produced this, and then `scripts/audit-sigma.mjs` — 160 lines,
written from the same two schema constraints — **found an eighth instance in the cyber track**,
in a phase whose claim verification has been marked complete since 2026-09-18. That is the
strongest argument in this repository for a guard over a pass: seven phases of careful reading
missed what a regex catches.

**The other `WRONG` findings, in the order they matter:**

- **`sigma check --fail-on-issues` does not do what the phase said it did**, in four places.
  pySigma's complete built-in validator list contains no validator that inspects
  `falsepositives` at all, so a reader following the phase would have built a CI gate that
  silently passed rules missing the field their review process cares most about.
- **A hunt query that returned nothing.** `| where X IN ("*\\a.exe", …)` — Splunk's `in`
  function forbids wildcards in its value list, and the `IN` operator honours them only with
  `search` and `tstats`, not `where`. No results reads as "no threats", so the control was
  silently absent rather than visibly broken.
- **A revoked ATT&CK technique.** `T1562.001` has been a bare redirect to `T1685` since v19, and
  the corpus cited it under its parent's name. Separately, **Defense Evasion is no longer an
  Enterprise tactic** — TA0005 is Stealth and TA0112 Defense Impairment is new — so three Sigma
  tags and two prose uses were naming a tactic the matrix retired.
- **An audit filter that missed its own target.** `OperationName` was compared against
  `Add member to role outside of PIM`; the documented string ends `(permanent)`, so the one
  operation the phase called "the interesting one" never matched.
- **A `kubectl describe` claim that was simply false.** The value is not printed for a
  `secretKeyRef`; kubectl shows a reference. Read from kubectl's own source.
- **An AWS CLI payload with the wrong shape.** `CloudTrailDetails` takes a `trails` *list* of
  objects keyed `cloudTrailArn`, with `accessRole`/`startTime`/`endTime` as siblings — the
  corpus nested them inside a single `trailArn`, which is not a member at all.
- **A NIST publication under its superseded title.** SP 800-50 Rev. 1 was retitled *Building a
  Cybersecurity and Privacy Learning Program* in September 2024. The existing NIST guard
  catches *withdrawn* publications; a retitle is a different rot class and is not covered.
- **One column off by a generation.** The prose credited `InitiatingProcessParentFileName` with
  naming the process that launched a LOLBin; that is the grandparent. The query beside it
  already used the right column.

**A verifier's `WRONG` verdict gets the same scrutiny as its `OK` verdicts, and this pass is
why that is worth saying twice.** The first report on the policy walkthrough concluded that a
deny statement "denies nothing the allow statement permits" — which is wrong; the JSON beside
it does re-deny five services. Reading the policy settled it, and the fix was one statement
number rather than the argument. D-038's rule is symmetric, and this pass is the case that
proves it.

because it will be acted on.

## What a clean result does NOT mean

**This is not a verdict on the curriculum.** It means the classes above were checked against
sources. The extractor cannot see a bad analogy, a misleading emphasis, or outdated practice that
reads as current — and those are the errors most likely to actually mislead a beginner. That
layer has only ever been tested by the comprehension passes, and it remains the largest
unexamined risk in the repository.

## What this file does NOT claim

- **It is not exhaustive of the content.** It finds claims of the classes above. Prose that is
  wrong in a way no pattern catches — a bad analogy, a misleading emphasis, an outdated practice
  — is invisible here and always will be.
- **It is not a comprehension check.** Whether a beginner can follow the text is a different
  question, answered by [`COMPREHENSION-AUDIT.md`](COMPREHENSION-AUDIT.md).
- **A clean result does not mean the phase is correct.** It means these classes were checked.
