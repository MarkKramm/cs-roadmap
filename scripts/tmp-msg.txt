2. FULL-TEXT SEARCH (D-013)

The obvious implementation was measured and rejected. Storing segment text came
to 473 KB gzipped because it duplicated every lesson file; an average lesson
gzips to 16 KB, so that index cost roughly thirty lessons of download for an
occasional feature. Windowing segments for better snippets was measured too and
made it WORSE (1438 -> 1501 KB), because overlap duplicates text.

What ships is an inverted index — term to segment id, no prose — built at build
time and fetched once, lazily, on the reader's first search. 180 KB as its own
chunk. index.html does not reference it, so the main bundle is unchanged at
105 KB gzipped and a reader who never searches pays nothing.

THREE SILENT-FAILURE BUGS, found by testing the index against the query engine
rather than by reading either one. All three returned nothing or the wrong thing
without erroring, which is the failure mode this repository keeps finding:
- Terms in >20% of segments were DELETED to save space. A query is an AND, so
  one deleted term killed the whole query: "user account locked" found NOTHING
  because "user" was gone. They are now kept and flagged — matched, but not
  allowed to narrow — and the UI reports which words it ignored.
- Trailing punctuation was glued into terms, so "...was timestomped." indexed
  "timestomped." separately from "timestomped".
- An exact match SUPPRESSED broader ones: searching "timestomping" matched only
  that term and never reached the stem finding module 11's "timestomped", so
  typing MORE precisely returned FEWER results. Exact and prefix matches are now
  tiered. Merging them flatly was wrong the other way: STAR exactly matches the
  interview method but also prefixes start/startup/starved, drowning the lesson
  that teaches STAR.

test:search guards all three plus ID range, ordering, empty and nonsense
queries. A search bug does not crash the page — it returns the wrong answer — so
the guard asserts on known-correct hits, not on the absence of exceptions.
